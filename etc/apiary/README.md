# Apiary sample configuration files

This directory holds one reference config file per daemon, installed by
`make install` next to the real config path on a node
(`/usr/local/etc/apiary/<name>.json.sample`).

There is no `apiaryctl.json.sample`, and that is not an omission.
`apiaryctl` - the operator command line, installed beside the daemons at
`/usr/local/libexec/apiary/apiaryctl` - has no configuration of its own.
It reads the daemons' config files above and the restart guardrail's
record directory, and every value it needs from either is already
documented where that value lives. A sample of nothing is not a document.

Every file here is **valid JSON as shipped**. It has no `//` lines, no
`/* */` blocks, and no trailing comments, because JSON has no comment
syntax and both `encoding/json` and this project's `internal/jsonstrict`
reject one. There is therefore no "strip the comments" step: copy the file
and it is already a complete, valid config.

```bash
cp /usr/local/etc/apiary/managerd.json.sample /usr/local/etc/apiary/managerd.json
chmod 600 /usr/local/etc/apiary/managerd.json
${EDITOR:-vi} /usr/local/etc/apiary/managerd.json
```

The guidance in `docs/bootstrap.md` Steps 7-9 and `docs/create-node.md`
Steps 5-7 still works unchanged: the `sed -e '/^[[:space:]]*\/\//d' -e
'/^[[:space:]]*$/d'` recipe those docs use is now a no-op, because there is
nothing left for it to remove.

This file is the place the explanatory prose lives. It used to be `//`
comments inside the samples themselves, where it was useful to nobody:
copy the sample verbatim and the daemon refused to start with a syntax
error, and the very operator who needed the explanation most was the one
who had just stripped it. `TestSamplesAreValidStrictJSON` in
`internal/configsamples` fails the build if a `//` or `/*` ever comes back
into a sample.

A sample is never read by a daemon. It is a template: substitute the
placeholders below, and keep the file root-owned and mode 0600 once it
holds a credential.

## Placeholders to substitute

| Placeholder | Files | Substitute with |
| --- | --- | --- |
| `<this-node-id>` | `managerd`, `raftd` | This node's stable ID, e.g. `node1`. Leave the key out entirely (not empty string) to fall back to `os.Hostname()`. Leaving the literal placeholder in place has previously committed `"<this-node-id>"` into raft state permanently — see `SHARED.md`. |
| `<this-node-hostname>` | `managerd.rpc_addr`, `frontend.manager_addr`, `restshimd.manager_addr` | This node's own DNS name, e.g. `node1.example.lab`. See "Bind versus dial" below. |
| `<this-host-address>` | `raftd.raft_bind` | This host's real, reachable address, e.g. `192.0.2.10`. |
| `<uplink-ifname>` | `managerd.uplink` | The physical interface VLAN-tagged networks attach to, e.g. `igb0`. |
| `<your-pool-name>` | `managerd.zfs_base` | An existing ZFS pool on this host, e.g. `tank`. The parent dataset must already exist; creation is intentionally non-recursive. |

## Bind versus dial: the one rule four fields depend on

An address a process **binds ON** is not the same kind of thing as an
address it **dials**, and the same string means opposite things in the two
roles. `0.0.0.0` and `::` are legal to bind to and illegal to dial:
FreeBSD refuses the connection to an unspecified address. This is
enforced in code by `internal/addrpolicy`, as two separately named
functions — `ValidateBindAddress` and `ValidateDialTarget` — precisely so
no call site can apply the wrong one by accident.

It is not theoretical. managerd's `rpc_addr` was documented as the
wildcard, operators copied that value into the fields that are *dials* —
restshimd's and frontend's `manager_addr`, and `cmd/raftd/confirm.go`,
which reads `rpc_addr` straight out of the other daemon's config — and a
live node logged:

```
cannot reach managerd at 0.0.0.0:17700 (connecting to
0.0.0.0:17700: dial tcp 0.0.0.0:17700: connect: connection
refused)
```

The wildcard bound perfectly, so managerd looked healthy while the two
daemons that carry the whole operator-facing API could not reach it at
all. A working listener is exactly what hides this class of mistake.

## Why a hostname, and the certificate SAN requirement

`rpc_addr`, `frontend.manager_addr` and `restshimd.manager_addr` all
name the node's **own DNS name**, not its numeric LAN address.

A serving certificate generated by `make setup`'s `setup-tls` (Step 6)
carries SANs `IP:127.0.0.1` and `DNS:<hostname>` and **no SAN for the
node's LAN address**. `cmd/raftd/confirm.go` leaves its TLS `serverName`
empty, so Go verifies managerd's certificate against whatever host was
dialed. A bare `10.90.0.x` therefore cannot verify — and neither can a
wildcard. The node's own DNS name is the one host that is in the
certificate. `manager_tls_ca` / `peer_tls_ca` only establish *trust in*
the certificate; they do not decide *which name* it must match.

Two consequences follow, and both are deliberate:

- A listener bound to the node's own name resolves to its LAN address, so
  it serves LAN clients but **deliberately does not serve `127.0.0.1`**.
  frontend and restshimd must therefore point `manager_addr` at that same
  hostname, not at loopback (ADR-0139).
- `managerd.rpc_addr` must not be `0.0.0.0`, for the dial reason above.
  The old loopback-only default `127.0.0.1:17700` is not an answer either:
  it leaves the node unreachable from its peers, so it does not work for a
  multi-node Colony.

## `managerd.json.sample`

This same file is what the **Machine Configuration** web page reads and
writes later, for every field except `node_id`, `rpc_addr` and
`raftd_socket`, which are deliberately not exposed there (ADR-0100).

`node_id`, `rpc_addr` and `raftd_socket` are not RPC-editable.

### `rpc_addr` serves three roles, and only one of them is "bind"

1. `net.Listen` on this address, for peers and for this node's own
   frontend/restshimd to connect to.
2. A **local dial target**. `cmd/raftd/confirm.go` reads this same
   `rpc_addr` and dials it to confirm a pending raftd restart to its own
   local managerd (ADR-0125). On FreeBSD a dial to `0.0.0.0:17700` is
   connection-refused, so a wildcard here leaves every raftd restart
   confirmation stranded.
3. The **port half only** of the peer-advertised manager address. The host
   half of that is derived independently, as `node_id` +
   `peer_hostname_suffix` — never from this field.

Replace `<this-node-hostname>` with this node's own DNS name, the same
name its serving certificate carries as a DNS SAN (ADR-0139).

### Write-once fields

`zfs_base`, `bhyve_prefix`, `iso_dir`, `jail_prefix` and
`jail_mount_base` are **write-once**. Existing datasets under an old value
would be silently orphaned, not moved, by changing one of them later, and
uploaded images would become invisible. Change them only before this node
has real state under the old value.

### Every field

- `node_id` — identity reported in Status responses. Leave the key absent
  entirely (not empty string) to fall back to `os.Hostname()`. Not
  RPC-editable.
- `rpc_addr` — the TCP address managerd's own external RPC API listens on.
  See above for all three of its roles. Not RPC-editable.
- `raftd_socket` — path to raftd's internal Unix socket this node dials at
  startup. Not RPC-editable.
- `uplink` — the physical interface VLAN-tagged networks attach to.
- `nat_uplink` — the interface a self-hosted network's outbound NAT
  egresses through (ADR-0048). Empty falls back to `uplink` above.
- `dhcp_dns_server` — the resolver address handed to DHCP clients on
  Apiary-managed networks. Node-local, because each Hive can have a
  different reachable resolver.
- `zfs_base` — WRITE-ONCE: base ZFS dataset for VM/jail resources
  (`<pool>/apiary`). The parent dataset must already exist; creation is
  intentionally non-recursive.
- `reconcile_interval` — pure tuning knob, safe to change any time. JSON
  stores Go durations as integer nanoseconds; zero uses the built-in
  default.
- `bhyve_prefix` — WRITE-ONCE, same reasoning as `zfs_base`.
- `bhyve_bootrom` — empty disables bhyve provisioning on this node
  entirely (nodes performing dataset-only reconciliation still work
  without this).
- `bhyve_bridge` — empty disables VM networking on this node.
- `allow_uplink_bridging` — gates whether this node will provision an
  `uplink_bridged` network (ADR-0101): VMs attached directly to this
  node's own bhyve bridge, sharing the host's own management broadcast
  domain. Must be exactly `yes-share-uplink-bridge` to opt in; any other
  value, including `true`, is treated as unset deliberately.
- `disk_size_mb` — only affects newly created VM disks, never resizes an
  existing one, so it is safe to change any time. Zero uses managerd's own
  built-in default.
- `iso_dir` — WRITE-ONCE, same reasoning as `zfs_base`.
- `hast_enabled`, `jail_enabled`, `peer_tls` — tri-state: omit the key
  entirely to use managerd's own startup default; `true`/`false` are
  explicit local overrides. `peer_tls: true` dials peer managerd instances
  over TLS.
- `jail_prefix`, `jail_mount_base` — WRITE-ONCE, same reasoning as
  `zfs_base`.
- `jail_disk_size_mb` — only affects newly created replicated jail roots,
  never resizes an existing one. Zero uses managerd's own built-in
  default.
- `peer_api_key` — a real credential if set (ADR-0029), and required once
  the Colony has any API key at all (ADR-0023), so every managerd can
  forward writes to and be forwarded to from its peers. This file must then
  be root-owned, mode 0600. Every Comb in one Colony shares the same
  value.
- `peer_managerd_port` — port assumed for a peer node's managerd external
  API when forwarding.
- `peer_tls_hostname_map` — comma-separated `ip=hostname` mappings, needed
  because raft leader hints contain bare IP addresses while real
  certificates are hostname-based. A missing mapping fails verification
  rather than weakening TLS.
- `peer_tls_ca` — a PEM file trusted instead of the system certificate
  pool when dialing a peer over TLS (ADR-0093); needed when peers present
  self-signed certificates.
- `known_peer_addresses` — comma-separated `host:port` allowlist
  (ADR-0097) that `target_address` must match on the three
  unauthenticated join-colony RPCs. Leave empty on a Comb's very first
  bootstrap, before any peer addresses are even known yet; safe to add
  once the Colony's membership is settled.
- `assumption_check_interval`, `assumption_heartbeat_interval`,
  `assumption_stale_after`, `assumption_run_deadline`,
  `assumption_history_limit`, `assumption_history_max_age` — pure tuning
  knobs for the assumption-checker subsystem, safe to change any time.
  JSON stores Go durations as integer nanoseconds; zero uses managerd's
  own built-in defaults.
- `tls_cert` / `tls_key` — managerd's own external API TLS. Mandatory, not
  an afterthought reserved for when `pam_service` is set. Setting both here
  makes managerd's whole gRPC listener TLS-only (frontend and restshimd
  must then set `manager_tls`/`manager_tls_ca` to still reach it), even for
  a purely loopback, single-node Comb. Points at Step 6's
  `make setup`/`setup-tls` output by default.
- `pam_service` — the PAM service name frontend's web UI logins are
  authenticated against. Empty disables login entirely, and the web UI is
  then open to anyone who can reach the port. Restart managerd **followed
  by** frontend after changing this; frontend checks PAM only at startup.
  See `docs/bootstrap.md` Step 11.
- `cloudflare_token_file` — a path to a Zone:DNS:Edit-scoped API token,
  never the raw token itself. An empty token file disables the whole
  feature.
- `cloudflare_zone_id`, `cloudflare_tunnel_id`,
  `cloudflare_tunnel_credentials_file` — the rest of the Cloudflare Tunnel
  exposure settings (ADR-0063).
- `origin_ca_token_file` — Cloudflare Origin CA issuance: a separate,
  zone-scoped credential, never a raw token or PEM directly.
- `origin_ca_directory` — local storage for the Origin CA material,
  separate from the Tunnel fields above.
- `origin_ca_renewal_check_interval` — how often to check local Origin CA
  certificates for ones due for automatic renewal. Integer nanoseconds;
  zero uses the default.
- `raftd_token` — shared secret presented to raftd's internal socket
  (ADR-0033), required if raftd's own `internal_token` is set. A real
  credential if set, so this file must be root-owned, mode 0600.

## `raftd.json.sample`

Only `data_dir`, `socket` and `node_id` matter for an independent
single-node Comb (`docs/create-node.md`). `raft_bind`, `join` and
`await_join` only matter when joining an existing multi-node Colony. The
current, safe flow uses `await_join` — see `docs/add-node-to-colony.md`.
**Do not** use an SSH tunnel to make `join` reach a remote Unix socket.

- `data_dir` — directory for raft's own log/stable store and snapshots.
- `socket` — Unix domain socket for the internal `RaftInternal` protocol;
  managerd dials this. Must live under a root-only directory
  (`/var/run/apiary` is created mode 0700 by `make setup`).
- `node_id` — unique ID for this raft node. Edit this: leaving the literal
  placeholder has previously caused a node to commit `"<this-node-id>"`
  into raft state permanently (see `SHARED.md`). Leave the key absent
  entirely, not empty string, to fall back to `os.Hostname()`.
- `raft_bind` — TCP address for the raft transport. Replace the
  placeholder with this host's real, reachable address. Do not use
  `0.0.0.0` here: the same value is advertised to Raft peers, which must
  be able to dial it.
- `join` — Unix socket path of an existing cluster member to join through
  (Path B only). Only ever consulted on a truly fresh, empty `data_dir`.
  Never point this at a world-searchable directory like `/tmp` — use
  `/var/run/apiary/` (root-only) instead.
- `await_join` — wait to be added as a voter rather than
  self-bootstrapping (ADR-0083), instead of setting `join` directly.
  Mutually exclusive with `join`.
- `internal_token` — shared secret required from every `RaftInternal`
  caller (ADR-0033). A real credential if set, so this file must then be
  root-owned, mode 0600 (already the default from `make setup`).
- `raft_tls_cert`, `raft_tls_key`, `raft_tls_ca` — Raft transport mutual
  TLS (ADR-0078). Leave all three empty for plain TCP, the common case.

## `frontend.json.sample`

- `manager_addr` — TCP address of managerd's external RPC API. Must match
  this node's own `managerd.json` `rpc_addr` **exactly, hostname and all**
  (ADR-0139); `127.0.0.1` does not work once `rpc_addr` names the node's
  own DNS name, because such a listener deliberately does not serve
  loopback. See "Why a hostname" above.
- `http_addr` — address to serve the web UI on. `0.0.0.0` is **deliberate
  and correct here**: the web UI is the operator's browser-facing surface
  and is meant to be reachable from the LAN. This is not an oversight to
  be "fixed" to loopback — contrast `restshimd.json.sample` below, which is
  loopback-only for a completely different reason. The port is fixed
  (ADR-0108).
- `manager_tls` — dial managerd over TLS instead of plaintext. managerd
  always serves TLS by default now (see `managerd.json.sample`'s own
  `tls_cert`/`tls_key`); leave this true unless managerd was specifically
  reconfigured without TLS.
- `manager_tls_ca` — PEM CA file to trust for managerd's certificate; empty
  trusts the system pool. Points at the same self-signed certificate Step
  6's `make setup`/`setup-tls` generated — managerd has no public CA to
  verify against otherwise.
- `manager_tls_server_name` — hostname to verify managerd's certificate
  against, if different from `manager_addr`'s own host.
- `tls_cert` / `tls_key` — serve the web UI over HTTPS, using Step 6's
  `make setup`/`setup-tls` output by default.
- `peer_tls` — dial other cluster nodes' managerd over TLS when fetching
  their host stats for the cluster overview page.
- `peer_tls_ca` — a PEM file trusted instead of the system certificate
  pool when dialing a peer over TLS (ADR-0093). Only consulted when
  `peer_tls` is set.
- `peer_hostname_suffix` — appended to a node ID to form its managerd
  hostname for the cluster overview page. Leave unset if node IDs are
  already fully qualified hostnames.
- `peer_manager_port` — port assumed for a peer node's managerd external
  API when fetching its host stats.
- `manager_api_key` — the API key frontend attaches to every call it makes
  to managerd on the logged-in user's behalf, once managerd has API-key
  auth enabled (ADR-0023). A real credential if set, so this file must
  then be root-owned, mode 0600.

## `restshimd.json.sample`

- `manager_addr` — TCP address of managerd's external RPC API. Must match
  this node's own `managerd.json` `rpc_addr` exactly, hostname and all
  (ADR-0139), for the same reason as `frontend.json.sample`.
- `http_addr` — address to serve the REST API on. `127.0.0.1`, **not**
  `0.0.0.0`, and that matches `internal/restshimdconfig`'s own built-in
  default. Nothing inside the Colony ever dials restshimd — the web UI has
  its own conversion path, and raftd, managerd and `apiaryinstall` never
  call it — so its only intended clients are external tooling: curl, CI, a
  future provider. Remote callers use an SSH local forward:

  ```bash
  ssh -L 8081:127.0.0.1:8081 <comb>
  ```

  Exposing this on the LAN is only worth considering once real managerd
  API keys exist; before then the `Authorization` header is decorative and
  the port is an unauthenticated control surface. The port is fixed
  (ADR-0108).
- `manager_tls` — dial managerd over TLS instead of plaintext. managerd
  always serves TLS by default now (see `managerd.json.sample`'s own
  `tls_cert`/`tls_key`); leave this true unless managerd was specifically
  reconfigured without TLS.
- `manager_tls_ca` — PEM CA file to trust for managerd's certificate; empty
  trusts the system pool. Points at the same self-signed certificate Step
  6's `make setup`/`setup-tls` generated.
- `manager_tls_server_name` — hostname to verify managerd's certificate
  against, if different from `manager_addr`'s own host.
- `tls_cert` / `tls_key` — serve the REST API over HTTPS, using Step 6's
  `make setup`/`setup-tls` output by default.

### restshimd has no authentication of its own

It has no static, process-wide manager API key of its own. Every external
caller presents its own bearer key, which every REST handler forwards
**unchanged** to managerd. There is no field for that here; it travels in
each request's own `Authorization` header. restshimd's entire security
boundary is therefore managerd's per-key auth — which is the other half of
why it stays on loopback.

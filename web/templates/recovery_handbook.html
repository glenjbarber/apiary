Comb loss

Scope of this edition

This edition covers exactly one scenario: the loss of a single named comb, including the special case where that comb currently holds raft leadership. It is generated fresh on every request from live cluster state - it is not derived from a persisted "Flight Plan" (that mechanism does not exist yet in Apiary).

Not covered by this or any current edition: management-network (control-plane) failure - distinct from the already-built managed tenant-network failure simulator; and the online Guided Recovery Mode, which depends on a Flight Plan execution engine that does not exist yet. Total control-plane loss and rebuilding from surviving storage - both previously unwritten here too - have static, hand-written procedures below instead: unlike the scenario above, that case cannot be generated from live cluster state, because by definition there is no live cluster state left to generate it from.

Total control-plane loss (every raft voter gone)

Distinct from losing one comb above: every raft voter's own state is gone or unreadable, not just one. This does not mean every VM/jail is gone - HAST-replicated and locally-provisioned disk data on each surviving comb's own ZFS pools is untouched by raft state loss. Only Apiary's own tracking of what existed is what this scenario threatens, and whether that tracking comes back depends entirely on step 2 below.

1. Confirm this is really total loss, not partial

On each comb, with apiary_raftd stopped, run raftd -status-json (reads the on-disk raft state directly - starts no server, contacts no peer, writes nothing). Any comb reporting a real term and log index is still intact - treat that comb as the recovery target for "loss of one comb" above instead of this section.

2. Locate a raftd -export archive

Apiary's own automated backup system explicitly excludes raft state (ADR-0131: "Backed up separately, by the operator, on their own schedule. Backup never writes raft state.") - recovery of the tracked VM/jail/network/API-key records depends entirely on whether an operator manually ran raftd -export <path> at some point and saved the result somewhere that survives every comb being gone at once. Check there now, before doing anything else below.

STOP: If no archive can be found, skip directly to step 5 below - steps 3 and 4 do not apply.

3. Validate the archive before trusting it

raftd -restore-dry-run <path> on any comb - read-only, no confirmation phrase, makes no changes at all. Confirms the archive's format version and checksum, and prints its export timestamp, source node ID, applied index, and record counts (VMs, jails, networks, API keys). Read this before committing to step 4: anything created after the export's own timestamp is not in the archive and will not come back.

4. IRREVERSIBLE: Restore onto one comb, then rejoin the rest

Restore is single-node-only (ADR-0051) - pick one surviving, healthy comb to become the new sole voter.

(a) Stop raftd there: service apiary_raftd stop.
(b) Wipe whatever raft state it has, even if none, so the data directory is genuinely empty: raftd -reset yes-wipe-raft-state.
(c) Restore: raftd -restore yes-restore-raft-state -restore-file <path> - this refuses outright if the data directory is not empty, which is exactly why (b) runs first.
(d) Start it normally: service apiary_raftd start - it detects the restored state automatically on this next start and does not bootstrap fresh.
(e) Rejoin every other surviving comb to this one exactly as if adding a new node (docs/add-node-to-colony.md) - the ordinary join path is unmodified by any of this.
(f) API keys restore as hash records only (ADR-0023) - any key an operator does not already have saved in raw form elsewhere cannot be recovered even by this restore; expect to reissue keys as needed afterward.

STOP: Do not run -restore against a comb whose data directory might still hold something real - confirm (a) and (b) completed, and that step 1's -status check showed nothing worth keeping on it, first.

5. No archive exists: rebuilding control-plane tracking from surviving storage

The raft-tracked records themselves - which VMs/jails/networks/API-keys existed, and their configuration - are unrecoverable. This is not the same as losing the actual VMs/jails: disk data on each surviving comb's own ZFS pools is untouched by raft state loss; only Apiary's own bookkeeping of it is gone.

(a) Bring up a fresh, single-node control plane on one surviving comb by following docs/bootstrap.md's "Path A - independent single-node cluster" exactly.
(b) On each comb, inventory what is actually still there before recreating anything: zfs list -r <pool>/apiary for VM/jail datasets, jls for running jails, the bhyve process list for running VMs.
(c) For each real, still-present resource found in (b), recreate the matching Apiary record by hand through the normal Create flow, using the discovered configuration rather than a guess - this re-establishes Apiary's tracking without touching the underlying disk data at all.
(d) Rejoin every other surviving comb normally (docs/add-node-to-colony.md).

6. Prevent a repeat

The single biggest determinant of how bad this scenario turns out to be is whether step 2 found anything. raftd -export takes seconds, requires no downtime, and makes no changes to the running cluster. Nothing in Apiary runs it automatically - ADR-0131 deliberately leaves this to the operator. Run it now, save the result somewhere that survives every comb being gone at once, and repeat it on a schedule.

# ADR-0035: leader-only read forwarding

## Status

Accepted

## Context

`GetVM`/`ListVMs`/`GetJail`/`ListJails`/`ListNetworks` have been leader-only reads since ADR-0009 - they read FSM state directly through raftd, which only answers for the current raft leader. This was never a practical problem while every deployment had exactly one node (always the leader), and stayed mostly academic even after real multi-node clusters existed, since leadership had no reason to move off the node an operator happened to be looking at.

That stopped being true the first time a real reboot actually moved leadership: restarting `apiarium`'s `raftd` as part of ADR-0033's rc.d hardening work caused a real election, landing leadership on `freebsd-apiary` instead. The result: `apiarium`'s own web UI could no longer show the VM list at all - `raft: this node is not the leader (leader hint: 10.50.0.11:17600)` - despite every other part of the stack (raftd, managerd, restshimd, frontend) working perfectly. Nothing was actually broken; this was always the correct, documented behavior of a leader-only read hitting a non-leader node. It just had never been *felt* until leadership genuinely moved.

ADR-0029 already solved the equivalent problem for *writes*: a rejected raft `Apply` (leader-hint set) gets forwarded to the leader's own `managerd` over the existing, already-authenticated `ManagerService` API, rather than exposing raftd's internal socket over the network. This ADR applies the identical idea to reads.

## Design decisions

- **Reuse `PeerReporter`, don't build a second forwarding mechanism.** `internal/manager.PeerReporter` already has a `dial(addr)` helper and an established pattern for reaching a peer's `managerd`. `ListVMs`/`GetVM`/`ListJails`/`GetJail`/`ListNetworks` are added to it as plain forwarding calls - dial the peer, call the exact same RPC, return its response verbatim. No new peer-to-peer RPC verbs needed (unlike ADR-0029's `Report*` methods), since the RPCs being forwarded are already public, already-shaped external API calls - a non-leader `managerd` acting as a plain client of the leader's own `ManagerService` is sufficient.
- **A read propagates the leader's actual answer; a write only propagates success/failure.** ADR-0029's `Report*` forwarding returns just an error (fire-and-forget from the reconciler's perspective - the write's effect is what matters, not a payload). A read has no side effect to skip; forwarding it and discarding the real answer would defeat the purpose. `Server.ListVMs` (etc.) return the peer's response directly on a successful forward.
- **Single-hop forwarding, with a plain fallback to the original error.** If the peer forward itself fails (peer unreachable, wrong `-peer-api-key`, etc.), the handler falls back to returning the original `LeaderHint` error rather than trying to chase a second hop - matching ADR-0029's own posture of not building a more general forwarding/routing mesh than the one real problem needs.
- **`PeerForwarder` is a new, narrow interface** (`ListVMs`/`GetVM`/`ListJails`/`GetJail`/`ListNetworks`) defined in `internal/manager`, satisfied by `*PeerReporter` - mirrors `internal/cluster`'s own `peerReporter` interface, which exists for the identical reason (letting a fake stand in for tests, avoiding a hard dependency on the concrete gRPC-dialing type).
- **One `*PeerReporter` instance, shared by the reconciler and the server.** `cmd/managerd` already constructs `manager.NewPeerReporter(*peerAPIKey)` for the reconciler's write-forwarding; the exact same instance is now also passed into `manager.NewServer` for read-forwarding, since both are forwarding to the same leader `managerd` over the same authenticated API - there's no reason for two separate peer clients or two separate credentials.
- **`peerManagerdAddr` duplicates `internal/cluster`'s `resolvePeerManagerdAddr` logic** (host from the leader-hint's raft-transport address, substituting the configured/default managerd port) rather than sharing it across the package boundary - the same small-duplication tradeoff `internal/cluster/peer.go` itself already documents for `defaultPeerManagerdPort`.

## Consequences

- `apiarium`'s (and any node's) web UI/REST API now work correctly regardless of which node currently holds raft leadership, as long as `-peer-api-key` is configured to match the cluster's actual auth state (same operational requirement ADR-0029 already established for write-forwarding) and the peer's `managerd` is reachable.
- Full unit test coverage of the new `PeerReporter` methods (`internal/manager/peer_test.go`), mirroring the existing `Report*` method tests exactly.
- **Real test-coverage gap, disclosed rather than papered over**: `Server.ListVMs`/etc.'s own wrapping logic (the `if s.peers != nil && resp.GetLeaderHint() != ""` check) has no integration test exercising a genuine raft leader-rejection, because `Server.raft` is a concrete `*RaftClient`, not an interface - unlike `internal/cluster`'s `Reconciler.Raft`, which is already an interface a fake can satisfy. Building a real two-node raft harness just for this was judged out of scope for this pass; the forwarding client logic itself (the part that actually talks to the network) is fully unit-tested, and the wrapping conditional is a small, direct mirror of the pattern `internal/cluster` already uses successfully. Verified live instead: after deploying to `apiarium` (currently a raft follower) with `-peer-api-key` set, its own web UI's VM list loaded correctly by transparently forwarding to `freebsd-apiary` (the actual leader).
- **Update**: TLS peer-forwarding was closed the same night this ADR was written, once rolling TLS out to `freebsd-apiary` made the plaintext gap immediately real rather than theoretical. `PeerReporter` gained `UseTLS bool` (`cmd/managerd`'s `-peer-tls`) and `PeerHostnames map[string]string` (`-peer-tls-hostname-map`) - the latter exists because a raft `leader_hint` is always a bare address (e.g. `10.50.0.11`), and Let's Encrypt never issues a certificate for a bare IP, so verifying the peer's real hostname-based cert needs an explicit IP-to-hostname mapping. A small static map, filled in once by an operator, is the right amount of machinery for this project's own small, fixed set of known nodes - not a general service-discovery mechanism. An IP with no map entry fails TLS verification loudly rather than silently skipping it. Live-verified: `apiarium` (TLS-enabled, `-peer-tls` on) successfully forwarded a `ListVMs` read to `freebsd-apiary` (also now TLS-enabled) over a real, certificate-verified TLS connection, using a new Viewer-role-only API key created specifically for peer-forwarding (deliberately not the Admin key otherwise in use, to cap the blast radius of a key that necessarily travels to every node in the cluster).
- Not addressed: automated certificate renewal *distribution* for `freebsd-apiary`/`freebsd-apiary2`/`freebsd-apiary3`. Their certs are issued and renewed by `apiarium`'s own `acme.sh` instance (reusing the same Cloudflare DNS-01 setup), but getting a renewed cert onto the actual target node and restarting its `managerd` isn't automated - that would need either passwordless root access from `apiarium` to each node (a real, separate security decision, not made here) or a manual step roughly every 60 days. Real, disclosed limitation, not silently deferred.

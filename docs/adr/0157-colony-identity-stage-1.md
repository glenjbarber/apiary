# ADR-0157: Colony identity, Stage 1 of ADR-0156

Status: Accepted
Supersedes: None
Superseded by: None
Affected projects: Apiary
Legacy identifier: ADR-0157 (Apiary)
Loreloom identifier: Pending allocation by Glen

## Status qualifications

Accepted means this record describes behaviour that is implemented in the tree, not a proposal.

This is the first of ADR-0156's six stages. ADR-0156 is the design document and remains the authority on the whole Colony Protocol; this record covers only Stage 1, which ADR-0156 scopes as "Colony ID only": the Colony ID in the replicated FSM, exposed in `StatusResponse`, carried on the join request and the pending join record, and a startup guard that refuses to self-bootstrap over a data directory that already belonged to a Colony.

ADR-0156's Stages 2 through 6 - epoch, sidecar and restore semantics, membership preconditions, divergence detection, and fencing tokens - are NOT implemented here. This record does not supersede ADR-0156, and ADR-0156's "Decisions for Glen" defaults that this Stage does not touch remain open.

The number 0157 is the next free apiary-local `docs/adr/` number after ADR-0156. Loreloom allocation is Glen's to do; `docs/adr/MIGRATION.md:31-37` requires central allocation for every shared identifier, so nothing here is padded or offset.

## Context

### Apiary has no colony identity anywhere

ADR-0156 records this as its central verified finding, and the finding still holds: `internal/raft/config.go` carries no colony ID, epoch, or incarnation field, and a search for `colony_id`, `colonyID` or `ColonyID` across `api/rpc/manager.proto`, `api/internalpb/raftd.proto` and `internal/raft/config.go` returns nothing.

Two independently bootstrapped `raftd` instances therefore form two unrelated clusters, and nothing in the system is able to detect it. Before this record, a node's own answer to "which Colony am I in" was never asked, because no such question could be answered.

### Why an identity held in configuration would not fix it

The obvious implementation is a `colony_id` field in `managerd.json` or in `raftd`'s own config, read by whichever node asks.

That does not close the gap. Two nodes with two config files still hold two different identities, and each is still certain it is alone. The problem is not that the identity is missing; it is that the identity is not something the members DERIVE TOGETHER. Only a value that comes from the committed log is derived together, and only such a value can make two voters of one Colony answer identically and two voters of different Colonies answer differently.

This is the same reasoning that put `ColonyJoinWindow` (ADR-0147) and `ColonyDiskSize` (ADR-0148) in replicated state rather than in a per-Comb config file, and it is why `internal/raft/colonydisksize.go` opens with that reasoning at length.

### The four things Stage 1 needs

ADR-0156's Stage 1 needs exactly four things:

1. A Colony ID in the replicated FSM, so that every voter holds the same value and every snapshot carries it.
2. A Colony ID in `StatusResponse`, so that a node can state which Colony it is in without an inference.
3. A Colony ID in the join payload, so that a join is authorized into a named Colony rather than into an unnamed one.
4. A startup guard that refuses to self-bootstrap when the node's own data directory says it was previously part of a colony and no join was requested.

The startup guard is the part with no precedent in the tree, and the part that does the most work. It is what turns ADR-0038's tiered reset (`cmd/raftd/main.go`) from a silently dangerous operation into an explicitly declared one.

## Decision

A Colony has exactly one identity. It is a random UUIDv4, generated by the node that bootstraps the Colony and committed through the replicated log as a single `SetColonyIdentity` command. It is never derived from the Colony CA fingerprint, and it is never rewritten.

### The identity lives in the replicated FSM

The FSM carries a single `ColonyIdentity` record (`api/internalpb/state.proto`), set by exactly one command and refused by every later one. The refusal lives in the FSM's apply function (`internal/raft/colonyidentity.go`), not in any handler, for the reason `internal/raft/colonydisksize.go` gives: a handler check is advisory and protects only the path that went through it, while the apply function runs in the same order on every replica, from the same committed log.

The record is inside `FSMSnapshotState`, so it is inside ADR-0143's state digest with no second list to forget - the digest is derived from the message descriptor rather than from a hand-maintained list of sections, so a new state field cannot silently escape it. A raft snapshot restore, or a seeded recovery via `raftd -restore`, therefore cannot drop the identity.

### The identity is set once and never rewritten

A second `SetColonyIdentity` is refused by name, naming both the existing and the proposed identity, so a node that lost a race learns that it lost rather than believing it succeeded.

A Colony identity is what every other fact is anchored to. If it could be rewritten, "the Colony I joined" and "the Colony I am in now" could differ, and the difference would be invisible - there would be no record of the old value to compare against.

A node that wants a different identity is not changing this Colony's identity; it is forming a new one. That is a different operation with a different answer, and ADR-0156's restore semantics - Stage 3 - own it.

### The identity is generated, not derived

The ID is a random UUIDv4 from `crypto/rand`, generated by the node that bootstraps the Colony.

ADR-0156's default is that the Colony ID is independent of the Colony CA fingerprint, and this record implements that default rather than deciding it. Keeping the two anchors INDEPENDENT is what lets the Colony CA be rotated without the Colony's identity changing, and it is what stops a certificate from silently becoming the Colony's name. A fingerprint-derived ID would couple the Colony's identity to the very value ADR-0156's CA-rotation problem wants to be able to change.

### Leadership is what establishes the identity, not startup

The identity is committed by the leader, and leadership is not fixed at startup. A node that starts as a follower cannot commit one; a node that later wins an election must; and a node that restarts into an existing Colony must not need a second one.

`internal/raft/node.go` therefore runs a leadership watcher that acts on every leadership acquisition. The "already set" refusal in the apply function makes every repetition harmless: the second attempt is refused by the FSM, and the watcher reads back the identity that WON. That read-back is also what makes the watcher correct under a race - two leadership acquisitions can both reach the commit point before either has committed, and the loser must return the winner's value, not an error.

### The identity is served from replicated state, never from configuration

`internalpb.StatusResponse.colony_id` and `rpcpb.StatusResponse.raft_colony_id` are served from the replicated record. A node answering from its own config file would be answering a different question - "what did this process believe when it started" - which is exactly the question two independently bootstrapped nodes would answer differently.

The empty string is a REAL state, not an error. It means this node has applied no `SetColonyIdentity`: either it predates this record, or it was restored from a snapshot that predates it. It is deliberately not reported as an error, because a node that has genuinely not been told yet can still answer every other question on the response.

### A join states which Colony it is joining

`rpcpb.RequestJoinColonyRequest.colony_id` carries the joining node's claim. The member recording the request compares it against its own replicated identity and REFUSES a mismatch, naming both identities.

That refusal is what makes "join THIS Colony" a decidable question rather than an assumption. Without it, a node that believes it is joining Colony A can be admitted into Colony B, and nothing would ever notice - because Colony B's identity would not be something either side was comparing.

An EMPTY claim is accepted. Every node built before this record sends no claim, and refusing those would break every existing join for no safety gain: a member that makes no claim inherits the Colony's identity from the Colony rather than asserting one.

A claim is compared only on the local-recording path, because that is the path where the receiving managerd IS the Colony member recording the request on its own raft. A request carrying `target_address` is relayed, and the member that actually records it runs the same check on its own authoritative view - gating on the relay as well would mean a follower could refuse on a stale identity while the leader would have accepted.

### The startup guard

`internal/raft/colonysidecar.go` adds a small JSON sidecar, `colony-identity.json`, in the node's data directory, recording which Colony that directory last belonged to.

The guard refuses to self-bootstrap when the sidecar is present. A node with an EMPTY data directory and no sidecar is a node forming a new Colony, which is legitimate - it is how every Colony starts. A node with an EMPTY data directory and a sidecar is a node whose data was wiped or moved aside, and self-bootstrapping there would form a second Colony that nothing could detect.

The sidecar lives OUTSIDE the wiped content but INSIDE the data directory, so `raftd -reset` - which MOVES the directory aside rather than deleting it - carries the sidecar with it. That is what makes a deliberate reset produce a genuinely fresh Colony, and it is what lets an operator see which Colony the moved-aside data belonged to.

The sidecar is a HINT that this directory used to hold state for some Colony. It is NOT the authority on identity: the replicated identity is. The guard REFUSES a self-bootstrap when the hint is present; it never decides which Colony the node is in.

A CORRUPT sidecar is a refusal, not a silent pass. Ignoring it would discard the only evidence the guard has, in favour of a guess.

## Consequences

### What gets better

- Two independently bootstrapped `raftd` instances now hold DIFFERENT identities, and each says so. The condition ADR-0156 records as verified and undetectable is now detectable.
- Every voter of one Colony answers `Status` with the same identity, because the answer comes from the same committed log entry.
- A join request that names the wrong Colony is refused at the boundary, before a request is recorded.
- A node whose data was wiped and restarted no longer silently forms a second Colony: the startup fails and names the Colony the directory belonged to.

### What gets worse

- The FSM has one more state field, and the state digest covers it, so a Colony's identity difference changes the digest. That is the intent: two voters disagreeing about the Colony's identity IS a state disagreement.
- A node that has been running for a long time and has no identity will acquire one the next time it becomes leader. A node that is never leader has no identity, and reports an empty one. That is honest - it genuinely does not know - but it is a new thing to look at in a status output.
- `raftd -reset` on a node whose data directory is NOT the one raftd is using, or a manually deleted `raft.db` leaving the sidecar behind, will produce a refusal where there used to be a silent re-bootstrap. That is the intended trade, and the refusal names the Colony and the fix.

### What this record does NOT do

- It does NOT implement ADR-0156's epoch (Stage 2), sidecar-and-restore semantics beyond the startup guard (Stage 3), membership preconditions (Stage 4), divergence detection (Stage 5), or fencing tokens (Stage 6).
- It does NOT change ADR-0156's other "Decisions for Glen" defaults, each of which remains reversible by amending ADR-0156.
- It does NOT change the join AUTHORIZATION flow. A mismatched claim is refused; an absent claim is still admitted under the existing ADR-0147 rules.
- It does NOT derive the identity from the Colony CA fingerprint, and it does NOT implement CA rotation. ADR-0155's Colony CA and this record's Colony ID are deliberately independent anchors.

# ADR-0169: Prepared certificate reservations

## Status

**Proposed.** This record designs the reservation that lets one Comb
prepare a certificate for a Comb that has not joined yet, and the
delivery that hands it over. It is the Apiary-side decision behind the
confirmed operator workflow of preparing Host 2's certificate on Host 1
before Host 2 is brought online.

Supersedes: None
Superseded by: None
Tracking issue: #26 (the MCP work); this record implements the
certificate-preparation workflow agreed for the Cloudflare and
Let's Encrypt node certificate bootstrap.

## Context

A public certificate authority validates a hostname, not a machine's
right to be a member of this Colony. The two questions are separate
and must stay separate: the CA answers "does the holder of this
private key control host2.lab2.apiary.work", and Apiary answers "is
this Comb one of ours, and do its peers recognise it".

The pieces for the single-node half already exist. `internal/acme`
implements a DNS-01 issuer against a real ACME server through
Cloudflare, `internal/origincert` owns the issuance and installation
transaction, `internal/hostcert` owns the certificate evaluation gate
and the fingerprint format, and `internal/joincredential` owns a
sealed envelope addressed to a certificate.

What does NOT exist is the offline preparation workflow. The ACME
protocol does not deliver a private key - the key is the requester's,
and the CA only signs a CSR made with it. So a certificate prepared
before the joining Comb exists is a certificate whose private key was
generated by the PREPARER. That has consequences that have to be
designed rather than assumed, and this record is about them.

Three further facts from the existing tree shape the design:

  - The peer trust store (`internal/raft/peers.go`) is CREATE-ONLY.
    `applyPinTrustedPeer` refuses a `node_id` that is already pinned,
    and the proto's own comment says a rotation is `UnpinTrustedPeer`
    followed by a fresh `PinTrustedPeer` - "two visible acts in the log
    rather than one invisible one". A prepared certificate therefore
    cannot be introduced by an update to an existing pin, and this
    design does not try to.

  - The pin's fingerprint and expiry are RE-DERIVED by the FSM from
    the certificate itself, and a mismatch is refused. A prepared
    certificate is a normal certificate, so it satisfies that gate
    unchanged - which is the point: the trust store does not need to
    know that a certificate was prepared rather than issued locally.

  - The store's entries are the input to the derived `peer-ca.pem`
    writer, so a pin is a trust anchor for an identity somebody
    compared. Anything that writes a pin without a comparison needs a
    justification of its own.

## Decision

A **reservation** records that a certificate has been prepared for a
Comb that has not joined yet. It is a distinct record from a
`TrustedPeer` pin, and the separation is deliberate: a pin is a trust
anchor somebody compared, and a reservation is a pending intent.

**A reservation is bound to a joining node before it is deliverable.**
Binding happens when the join attestation identifies the actual
joining Comb and the join request it belongs to. Before that, the
reservation names a FQDN and nothing else, and nobody may collect its
material. Knowing the reservation identifier, or the hostname, or the
join request ID is not authority to collect anything - the
reservation's delivery token is, and that token is generated at
random and compared in constant time.

**Binding is single.** A reservation bound to one join request cannot
be re-bound to another. A re-bind would hand the prepared private key
to a different machine, which is the one failure this design exists to
prevent.

**The delivery is sealed to the joining Comb's own certificate.** The
envelope is addressed to the certificate the joiner presented during
the attestation - the same certificate its peers will pin - so the
prepared private key is readable by that machine and by nobody else.
The associated data binds the envelope to the reservation ID, the join
request ID, the node ID and the certificate fingerprint, so a
ciphertext copied from one reservation's delivery cannot be opened
under another's: it fails to decrypt rather than decrypting into the
wrong joiner's key.

**The receiver re-derives rather than believes.** On opening a
delivery, the receiver recomputes the certificate's fingerprint from
the PEM that arrived, checks that the certificate covers the reserved
name, and checks that the private key matches the certificate. The
sender's own claim about any of these is not evidence. A certificate
for the right key but the wrong hostname would install cleanly and
then fail every handshake with a name mismatch, which is a much worse
place to discover it.

**The lifecycle is forward-only.** `prepared` -> `delivered` ->
`adopted` -> `retired`, with `withdrawn` and `expired` as terminal
exits from `prepared`. A reservation that has been delivered cannot be
delivered again; that is a property of the state machine rather than a
check each caller has to remember to write.

**The delivery window is bounded.** A prepared pair sits on the
preparing Comb holding a private key for a machine that has not
arrived yet, and an unbounded reservation is an unbounded wait. An hour
covers a window in which an operator prepares a host and then brings
it up, and is short enough that a forgotten reservation expires rather
than sitting in a protected store indefinitely.

**The bootstrap key is retired, not merely superseded.** The joiner is
expected to generate its own key and obtain its own replacement
certificate once it has taken ownership. Until it does, the preparer
holds a copy of a key that two machines hold, and that is the cost of
this mode. `retired` is the state that records the end of that
exposure, and it is a distinct, explicit act rather than a side
effect.

**A reservation is never a member.** It does not appear in the peer
trust store, it does not imply membership, and it is promoted by the
join flow's own authorization - never by the existence of the
reservation.

## Consequences

- Host 1 can prepare a working certificate pair for Host 2 while Host 2
  is offline, and Host 2 can collect it during the join.
- The prepared pair is a real certificate, not a special kind. It
  satisfies `internal/hostcert`'s evaluation gate unchanged, and its
  fingerprint is the same string the peer trust store pins.
- The private key of a prepared certificate has two holders until the
  joiner replaces it. The design states that cost rather than hiding
  it, and `retired` is the state that ends it.
- The delivery envelope reuses `internal/joincredential`'s existing
  sealed-envelope machinery and its existing associated-data discipline,
  so there is one implementation of "sealed to a certificate" rather
  than two.
- The integration configuration - the Cloudflare token, the zone, the
  ACME account - is NOT carried in the delivery bundle. It travels in
  its own protected channel, so that revoking a prepared certificate
  does not also revoke the ability to obtain a replacement.
- This record defines the reservation and the delivery. The trust
  TRANSITION - staging the next identity, activating the pair,
  acknowledging it, and retiring the old one - is a separate decision,
  because it has to extend the peer trust store's create-only pin
  lifecycle, and that extension is its own design question.

## Alternatives and consequences

- **Issue the certificate on Host 2 itself, after it joins.** Simpler,
  and it avoids the two-holder key entirely - but it cannot serve the
  confirmed workflow, which is preparing Host 2's certificate before
  Host 2 exists.
- **Transfer a CSR-producing key only, and let Host 2 request the
  certificate.** This avoids exporting a key that Host 2 generated
  before it joined, and it is a real alternative - but it cannot fully
  prepare a working pair before Host 2 has a key of its own, so it is
  a mode alongside this one rather than a replacement for it.
- **One wildcard certificate for the whole Colony.** Much simpler to
  distribute, and it makes the impact of one compromised Comb the
  impact on every Comb. Exact per-node certificates are the default.
- **Reuse one shared private key for every prepared certificate.**
  Rejected outright: a single key that can serve any node's identity
  is a key that can impersonate any node.

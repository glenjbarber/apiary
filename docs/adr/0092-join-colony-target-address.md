# ADR-0092: Join-a-Colony needs a real target address

## Status

Accepted

## Context

ADR-0083's own "Decision" section describes `RequestJoinColony` as being
called "on the target - the address of one existing Colony member the
operator names." No such addressing mechanism was ever actually built:
`RequestJoinColonyRequest` had no field for a target address, and the
handler only ever raft-`Apply`s a `PendingJoinRequest` onto whichever
managerd happens to receive the call (with leader-hint forwarding only
*within* that same, already-known raft cluster).

A real user hit this directly. Following the Machine page's own field
labels ("This Comb's node id" / "This Comb's raft-bind address") and
ADR-0083's own flow description ("Joining Comb's operator, on the
Machine page... enters this Comb's own node_id/raft_bind_address"), they
submitted the "Join a Colony" form on the *joining* node's own Machine
page, entering the *existing* Colony member's identity into fields that
actually meant "record this identity as wanting to join whichever
Colony receives this call." The result: a `PendingJoinRequest` silently
recorded on the joining Comb's own standalone single-node Colony,
claiming (backwards) that the existing Colony member wanted to join
*it* - invisible on the real target's "Pending join requests" panel,
and confusing to debug precisely because nothing errored. Diagnosing it
required dialing `GetJoinRequestStatus`/`ListJoinRequests` directly
against each managerd's own gRPC port to see where the record actually
landed.

Asked how far to fix this, the user chose building the real mechanism
ADR-0083 always described, over a copy-only fix that would have kept
today's "submit the form on the target's own page instead" workaround
in place.

## Decision

### `target_address` on the three requester-side RPCs

`RequestJoinColonyRequest`, `GetJoinRequestStatusRequest`, and
`CancelJoinRequestRequest` each gain an optional `string target_address`
field - the existing Colony member's own managerd address (`host:port`)
to reach. Only the requester-side operations need it: `ApproveJoinRequest`/
`RejectJoinRequest`/`PurgeJoinRequest`/`ListJoinRequests` are already
performed by an Admin logged into the Colony that actually holds the
record, so there is nothing to redirect there.

Each handler in `internal/manager/joincolony.go` checks `target_address`
first: when set, the call never touches this managerd's own raft at
all - it dials `target_address` via the existing `PeerReporter` (`s.peers`,
already used for ADR-0083's own leader-hint forwarding) and relays the
call there verbatim, stripping `target_address` from the forwarded copy
(routing information for this one hop, not part of what the target
should record). A `nil` `s.peers` (no peer forwarding configured on this
node) or a dial/RPC failure surfaces as a plain error in the response,
never a silent fallback to local recording - that silent fallback is
exactly the bug this ADR closes. Empty `target_address` preserves
ADR-0083's original behavior unchanged (direct callers/tests that
intend to record locally still can).

`PeerReporter` already had a `RequestJoinColony`/`CancelJoinRequest`
forwarding method (built for ADR-0083's own leader-hint forwarding) -
reused as-is. It gained one new method, `GetJoinRequestStatus`, needed
because a forwarded request's status now genuinely lives on a different
Colony member than the one polling for it.

### Frontend: the form now asks for the target explicitly, and requires it

`web/templates/machine.html`'s "Join a Colony" form gained a required
"Existing Colony member's address" field, submitted first. `target_address`
is required at the HTTP-handler level too (`handleRequestJoinColony`
returns a clear form error if it's blank), not just via the HTML
`required` attribute - submitting this form with no target is exactly
the confusing trap this ADR closes, and it should never be possible to
fall into by accident again.

The redirect after a successful request now carries both
`join_request_id` and `join_target_address` in the query string, so a
page reload/"Refresh status" keeps polling the same request via the
same target - `GetJoinRequestStatus` is otherwise purely local, and
polling without the target would immediately fail "not found" against
this node's own unrelated raft. The Cancel form's hidden fields carry
`target_address` through the same way.

With this fix, the code shown on the joining Comb's own screen is
generated by whichever managerd actually raft-Applies the record (the
real target, now reached directly) - the human-correlation check
ADR-0083 originally described (two different screens showing the same
code) is now genuinely meaningful, rather than moot because whoever
filled out the form already knew exactly which node they'd typed in.

## Consequences

- `internal/manager/server.go`'s `PeerForwarder` interface and
  `internal/frontend/cluster_overview.go`'s `peerHostStatsClient`
  interface both gained `GetJoinRequestStatus` - every test double
  implementing either (three in `internal/frontend`: `fakePeerHostStatsClient`,
  `slowRecoveryPeerClient`, `fakeISOPeerClient`) needed a stub, the same
  recurring mechanical cost as every prior RPC addition to these
  interfaces this project has hit before.
- New unit tests in `internal/manager/joincolony_test.go` cover the
  forwarding branch directly (nil-peers error path and a
  forwards-to-the-named-address-with-target_address-stripped path) for
  all three RPCs, using a fake `PeerForwarder`. No new two-real-managerd
  integration test was added - this project's existing peer-forwarding
  logic (ISO fetch, jail template fetch) is tested the same way, at the
  unit level with a fake forwarder, not with two live gRPC servers
  talking over a real socket; this stays consistent with that.
- New frontend tests cover: the target-address-required rejection
  (confirming `RequestJoinColony` is never called without one), a
  successful submission threading `target_address` into both the
  outbound RPC and the redirect's query string, and a status poll
  forwarding `target_address` through to `GetJoinRequestStatus` while
  echoing it back into the Cancel form's hidden field.
- `docs/adr/0083-mutually-authorized-colony-join.md` gained a
  "Corrected by ADR-0092" note at its own Consequences section,
  rather than being silently rewritten - the original ADR's design
  intent was right, only its implementation was incomplete.
- Full `go build ./...`, `go vet ./...`, `go test ./...`, `gofmt -l .`
  all clean.

## Correction (2026-09-11, ADR-0096)

`target_address` being caller-supplied on RPCs deliberately exempt from
`checkAuth` had a real, unaddressed consequence: the three handlers
dialed it via the same authenticated `PeerReporter.dial`, which
attaches this node's own `-peer-api-key` whenever one is configured -
regardless of whether the dialed address was ever a real, trusted peer.
An unauthenticated caller could name any host they controlled and
receive this node's shared peer secret. ADR-0096 adds
`dialUnauthenticated`/the three `*Unauthenticated` `PeerReporter`
methods, used only for this field; the trusted, internally-derived
leader-hint forwarding paths this ADR also touches are unaffected and
still authenticate normally.

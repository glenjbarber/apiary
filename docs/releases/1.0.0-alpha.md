# Apiary 1.0.0-alpha

The first public release of Apiary.

An alpha is a working system with its rough edges showing. This one
runs real virtual machines and real jails across a raft-consensus
cluster of FreeBSD hosts, and it says plainly where it stops.

## What a Comb is, and what a Colony is

An Apiary **Comb** is one FreeBSD host running an Apiary installation.
A **Colony** is one or more Combs that have agreed to be a single
cluster, with one of them holding leadership at any moment.

Each Comb runs four services:

| Service | What it does | Where you see it |
| --- | --- | --- |
| `apiary_raftd` | The consensus layer. Holds the Colony's replicated state. | Never directly. |
| `apiary_managerd` | The authority. Every state change goes through it. | Never directly. |
| `apiary_frontend` | The web UI. | <http://localhost:8080> |
| `apiary_restshimd` | A REST view of the same API, for external tools. | <http://localhost:8081> |

`apiaryctl` is the command line for the things that must happen on a
headless host, which is in practice every node that is not your desk.

## What it does

- **Real VMs.** A bhyve virtual machine with its own ZFS dataset, its
  own tap device on a host bridge, a VNC framebuffer for the console,
  and installer media attached as a CD-ROM or a second disk depending
  on what the file actually is — detected by sniffing the image, not by
  trusting its name. Deleting a VM tears the host-side resources down
  for real, and the reconciler's progress is what the UI shows, not
  what was requested.
- **Real jails.** A FreeBSD jail with its own dataset and networking,
  with the VNET addressing and the epair tracking that a real jail
  needs.
- **Real storage replication.** A VM can name a replica node and its
  disk is replicated there through HAST. The upstream `hastd` bug that
  used to block this was diagnosed, reported upstream, and is now
  fixed in every supported FreeBSD release — so a stock install needs
  no local patch.
- **A console that works from any machine.** bhyve's VNC listener is
  loopback-only and never exposed on the network. The web UI reaches
  it through an authenticated gRPC hop, and the managerd on the far
  side independently re-validates ownership before dialling. A
  caller-supplied host or port is never accepted.
- **A UI that refuses to guess.** Every status has a defined "not
  observed" state, distinct from "ok" and from "failed". A Comb that
  could not be reached is *unknown*, not healthy. There is no
  presentation of a missing value as a real one.
- **A safe join.** Joining a Colony is a two-person flow: the joining
  Comb shows a code, an Admin on the existing Colony compares it
  against the same code on their own screen and approves, and a second
  approval from a different API key is required. The joining Comb
  receives the Colony's certificate authority **only** against a
  fingerprint the operator compared by hand.
- **A consensus layer with a colony identity.** Before this, a second
  raftd that bootstrapped into a colony it did not belong to formed a
  second, unrelated cluster that nothing in the system could detect.
  Now every member carries a replicated colony identity, a colony-wide
  generation counter, and a rule that a restore is a colony
  re-creation rather than a member rejoin.

## What it does not do

These are real limitations, not a list of future ideas. The README
states them in more detail.

- **No automatic failover.** HAST replication is data redundancy. A
  replica's dataset is not cleaned up once its record is fully purged.
- **No scheduler.** Nothing decides which node a VM runs on beyond
  what a caller sets directly. `MigrateVM` and `MigrateJail` exist,
  but only as a manual, explicit operator action.
- **No jail console.** An interactive jail console was built, shipped,
  and then removed entirely, because a jail's root shell shares the
  host's kernel with no hardware isolation boundary and every
  mitigation built for it reduced but never eliminated that risk.
  Direct host access is the only way to get a shell inside a jail.
- **No VNC encryption on the underlying console connection.** It
  relies entirely on the login gate in front of it.
- **The Colony Protocol is three stages of six.** Colony identity, the
  generation counter, and restore semantics are done. Membership
  preconditions, divergence detection, and fencing tokens are not.
- **The Colony's certificate authority does not rotate, and its leaves
  are not renewed.** A leaf issued at join expires in about a year.
- **The Create form does not block automatically on incomplete
  teardown.** The operator checks the teardown panel first.
- **The `apiary-mcp` connector is installed but off by default**, and
  the Watchgoose monitoring integration and the Zabbix template are
  separate artifacts that a port's install does not wire up. The
  `versioncheck` tool is deliberately not installed either: it is a
  diagnostic an operator runs from a checkout, not something a
  running Comb needs.

## Installing

The intended distribution is the FreeBSD Ports Collection. A packaging
skeleton is in the repository for a port maintainer to complete.

From a source checkout, `docs/create-node.md` brings up a standalone
Comb and `docs/add-node-to-colony.md` adds one to an existing Colony.
`docs/HANDBOOK.md` is the operator's document.

**Apiary targets FreeBSD 15.** The minimum supported major version is
not yet decided between 14 and 15; the first alpha is built and tested
against 15.

## The documentation

There are **186 architecture decision records** in `docs/adr/`. Each
one says what was decided, what was rejected and why, and where the
decision stops working. Several of them record bugs that were found
by following the design to its conclusions.

Two documents are worth reading first:

- `docs/HANDBOOK.md` — what Apiary is, and how to operate it.
- `docs/adr/0156-colony-consensus-protocol.md` — the consensus layer's
  design, and what remains of it.

## The version scheme

This release is `1.0.0-alpha`, and it is deliberately distinct from
the later compatibility-based scheme, where an Apiary major version
reflects the lowest compatible FreeBSD major version (so a future
`Apiary 15`). The compatibility-based scheme and the `release/` and
`stable/` branches arrive once the codebase stabilises; see
`docs/release-process.md`.

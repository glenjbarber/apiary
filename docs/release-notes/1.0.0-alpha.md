# Apiary 1.0.0-alpha

**Tag:** `v1.0.0-alpha`
**Date:** 2026-10-27
**Status:** prerelease. The interface is not stable and a later alpha may
break it.

Apiary is a FreeBSD-native virtualization management platform for cluster
management, VM and container orchestration, storage replication, and a web
frontend. This is its first public release.

The repository's first commit is 2026-08-28; this release covers the
~1,240 commits since, which produced 185 architecture decision records in
[`docs/adr/`](../adr/).

## What this release is

A working, end-to-end Apiary. Every layer from consensus up to a browser
is implemented and tested, and real virtualization happens underneath it
without being asked for.

**The daemons.** Eight binaries:

| Binary | What it does |
| --- | --- |
| `raftd` | The consensus agent. HashiCorp's Raft, BoltDB-backed, over its own Unix-socket protocol. Single-node bootstrap, join, member removal. |
| `managerd` | The management daemon. Exposes the external gRPC API and runs the per-node reconciliation loop that actually provisions and tears down storage, VMs, jails, and networks. |
| `frontend` | The web UI. Server-rendered HTMX, one self-contained binary, no client-side JavaScript framework. |
| `restshimd` | REST-over-gRPC translation of the external API, with per-request auth forwarding. |
| `apiaryctl` | The operator CLI, for the things an operator types during an incident, when there is no checkout on the host. |
| `apiaryinstall` | Host preflight and provisioning. Checks every FreeBSD prerequisite and fixes the safe ones. |
| `versioncheck` | Compares the running binary against the on-disk one, so "is this Comb running what I installed?" has an answer. |
| `apiary-mcp` | A read-only MCP server, so an agent can read Apiary's state. |

**Virtualization.** Real `bhyve` VMs and real jails, under one
"cell" abstraction. VMs get a ZFS disk, a `tap` device on a host
bridge, a VNC framebuffer for a browser console, optional CD-ROM or
second-disk installer media, and optional serial-console log capture
([ADR-0010](../adr/0010-bhyve-vm-lifecycle.md),
[ADR-0007](../adr/0007-jail-lifecycle.md),
[ADR-0032](../adr/0032-bhyve-serial-console-log.md)).

**Storage.** ZFS dataset lifecycle, per-VM, managed by the reconciler
([ADR-0006](../adr/0006-zfs-dataset-lifecycle.md)). Base disk images can
be uploaded and reused, and a VM's disk can be expanded in place
([ADR-0031](../adr/0031-vm-base-images.md),
[ADR-0153](../adr/0153-configurable-base-image-disk-expansion.md)).
VM snapshot and restore, node-local ([ADR-0090](../adr/0090-vm-snapshot-restore.md)).

**Replication.** Real HAST-backed VM disk replication
([ADR-0026](../adr/0026-hast-vm-disk-replication.md)), with the
replication transport itself TLS-encrypted
([ADR-0158](../adr/0158-hast-transport-tls.md)).

**Networking.** VLAN networks, DHCP-backed IP allocation, and per-VM
`pf` firewall rules with an explicit priority
([ADR-0022](../adr/0022-network-management.md),
[ADR-0075](../adr/0075-firewall-rule-priority.md)). Managed networks
can share a real external gateway ([ADR-0047](../adr/0047-external-gateway-networks.md))
or carry the Colony's own outbound NAT
([ADR-0048](../adr/0048-self-hosted-outbound-nat.md)).

**The Colony.** Multi-node clustering with real join, membership
management, and leader election
([ADR-0003](../adr/0003-raftd-multi-node-clustering.md)). Joining is a
mutually-authorized, UI-driven handshake modeled on device pairing
([ADR-0083](../adr/0083-mutually-authorized-colony-join.md)), hardened
against an unauthenticated reachability oracle and a pre-approval
reachability check ([ADR-0096](../adr/0096-security-audit-follow-up.md),
[ADR-0097](../adr/0097-join-flow-hardening.md)). Cross-node forwarding
carries reads, writes, consoles, and serial logs
([ADR-0029](../adr/0029-cross-node-write-forwarding.md),
[ADR-0065](../adr/0065-cross-hive-console-tunnel.md)).

**Security.** TLS between the daemons, with a Colony CA and per-node
leaf issuance ([ADR-0155](../adr/0155-colony-certificate-authority.md),
[ADR-0186](../adr/0186-join-time-colony-ca-distribution.md),
[ADR-0187](../adr/0187-join-time-raft-leaf-issuance.md)). Tiered
RBAC (Viewer/Operator/Admin) with PAM-backed login and API keys
([ADR-0030](../adr/0030-tiered-rbac-pam-login.md),
[ADR-0023](../adr/0023-api-key-authentication.md)).

**Operations.** Evidence-aware health, automated assumption checks, a
dependency-graph simulator for "what if this node disappears?", a
resilience coverage map, an offline recovery handbook, and a controlled
one-Comb-at-a-time Colony update
([ADR-0052](../adr/0052-dependency-graph-simulator.md) through
[ADR-0062](../adr/0062-resilience-coverage-map-v1.md),
[ADR-0145](../adr/0145-controlled-colony-update.md)).

**Integrations.** A native monitoring API over RPC and REST
([ADR-0160](../adr/0160-native-monitoring-api.md)), a Zabbix template
checked against its own ADR
([ADR-0168](../adr/0168-zabbix-template-implementation.md)), and a
model-agnostic MCP tool surface
([ADR-0162](../adr/0162-apiary-mcp-server.md),
[ADR-0166](../adr/0166-model-agnostic-mcp-tool-surface.md)).

## What this release is not

Read this section. It is the difference between an alpha and a lie.

**The interface is not stable.** This is an alpha. The RPC and REST
surfaces may change in a way that breaks a caller in the next alpha.
That is what "alpha" means here.

**No compatibility promise beyond the floor.** The floor is **FreeBSD
15.1-RELEASE**, and this release makes no promise above it: the
interface may change in a way that breaks a caller in the next alpha.
What the floor means concretely is that on FreeBSD 15.1-RELEASE and
later, Apiary needs no locally patched `hastd`/`hastctl`, because the
fixes Apiary depended on are upstream
([ADR-0181](../adr/0181-hastd-fixes-in-freebsd-15-1-release.md)).

**No automatic failover.** HAST replication is *data redundancy*. When
a replicated VM's primary Comb dies, the replica holds the data; nothing
moves the VM over on its own. This is a disclosed limitation, not a bug
([ADR-0026](../adr/0026-hast-vm-disk-replication.md)).

**No scheduler.** Nothing decides which Comb a VM should run on beyond
what a caller sets directly. `MigrateVM` and `MigrateJail` exist and are
real, but they are manual, explicit operator actions
([ADR-0028](../adr/0028-migrate-vm-and-jail.md)).

**No interactive jail console.** A `jexec`-based jail console was built,
shipped, and then removed at the owner's request: a jail's root shell
shares the host kernel with no hardware isolation boundary, and every
mitigation reduced but never eliminated that risk
([ADR-0068](../adr/0068-jexec-jail-console.md)). Direct host access
remains the only way to get a shell inside a jail.

**No disk-format conversion, and UEFI only.** Importing a VM from
another hypervisor does not convert its disk, and the caller must supply
an already-raw, already-bootable image. Linux containers have no path
at all — jails share the host's FreeBSD kernel.

**No VNC credential encryption on the console connection itself.** The
console relies on the login gate in front of it
([ADR-0020](../adr/0020-novnc-console.md),
[ADR-0065](../adr/0065-cross-hive-console-tunnel.md)).

**Some replica data is not reclaimed automatically.** A replica's
dataset is not cleaned up once its VM's record is fully purged. This is
a deliberate consequence of never inferring teardown from an absent
record ([ADR-0026](../adr/0026-hast-vm-disk-replication.md),
[ADR-0027](../adr/0027-jail-orchestration.md)). An explicit
`CleanupOrphanedHASTResource` action exists for the operator
([ADR-0073](../adr/0073-orphaned-hast-resource-cleanup.md)).

**Terraform support is not built.** The infrastructure it would need -
the API-key-authenticated management API and the REST translation
layer - is in the tree. The provider itself is not; see the README's
"Tabled for now" section.

**A Colony-wide load-balancer or HA control plane is not built.** This
applies to the separate `cluster-api-provider-apiary` project, which
drives Apiary through the REST API; see its own README.

**The Colony Protocol is three stages of six.** Colony identity, the
colony-wide generation counter, and restore semantics are implemented
and shipped in this release. Membership preconditions, divergence
detection, and fencing tokens are **not** — see
[ADR-0156](../adr/0156-colony-consensus-protocol.md) for what each
would do. A Colony is therefore protected against a second raftd
bootstrapping into a colony it does not belong to, and is not yet
protected against a membership change that strands a quorum or against
two members whose state has diverged.

**The full, authoritative list of gaps is the README's "Not yet
implemented" section**, and it is longer than this summary. Read it
before deploying: [README.md § Status](../../README.md#status). This
release does not restate that list here, because a copy is a list that
drifts. The Colony Protocol's stage count is the one exception, because
it is not in the README and a reader would otherwise assume the design
is complete.

## Installing

This release installs onto a FreeBSD host you already have. There is no
ISO, no image, and no installer media — see
[`docs/release-process.md`](../release-process.md) for why.

```sh
git clone --branch v1.0.0-alpha https://github.com/glenjbarber/apiary.git
cd apiary
make install
make setup
```

`make install` puts the binaries in `/usr/local/libexec/apiary/`,
`make setup` writes the `rc.d` scripts, the PAM policy, and the
directories. Then follow the bootstrap guide:
[`docs/create-node.md`](../create-node.md) for a single-node Colony, or
[`docs/add-node-to-colony.md`](../add-node-to-colony.md) to add a Comb
to an existing one. The operator's reference is
[`docs/HANDBOOK.md`](../HANDBOOK.md).

`go install github.com/glenjbarber/apiary/cmd/apiaryctl@v1.0.0-alpha`
also works, and is convenient for a developer or a CI job. It is **not**
the deployment path: `go install` produces no `rc.d` script, no sample
config, no PAM policy, and no build identity stamp.

### Checking what you installed

Every binary reports its own identity:

```sh
/usr/local/libexec/apiary/raftd -version
```

A release build reports its version, its commit, and the date of that
commit:

```
raftd build=608e03f5182a version=1.0.0-alpha commit=608e03f5182a built=2026-10-27T15:15:58-04:00 go=freebsd/amd64
```

`versioncheck <host>` compares the running binary against the on-disk
one across the Colony, because a copy over a running executable leaves
the new bytes on disk and the old ones resident in the process.

## Verifying the release

The binaries are reproducible: the same commit, built twice on the same
toolchain, produces the same bytes. That is checked by
`make check-reproducible`, not asserted. The release's checksums are
published with the GitHub release.

To build from the tag yourself and confirm it:

```sh
git clone --branch v1.0.0-alpha --depth 1 https://github.com/glenjbarber/apiary.git
cd apiary
make build
make check-ldflags
make check-stamped
make check-reproducible
test -z "$(gofmt -l .)"
go vet ./...
go test -race ./...
```

Six packages shell out to FreeBSD-only tools and skip their integration
tests off FreeBSD: `internal/bhyve`, `internal/cluster`, `internal/hast`,
`internal/jail`, `internal/localraft`, `internal/zfs`. A release is cut
on a FreeBSD host, where they run.

## The design

185 ADRs in [`docs/adr/`](../adr/), in order, each recording the
decision and why it was made. They are the project's memory: for what
something does and, more usefully, what it deliberately does not do.

Three reading orders, depending on what you want:

- **What does this do?** The README's [Status](../../README.md#status)
  section, then the ADRs it links.
- **How do I operate it?** [`docs/HANDBOOK.md`](../HANDBOOK.md), then
  the runbooks in `docs/`.
- **Why is it built this way?** `docs/adr/`, from ADR-0001 forward.

## The next release

The version scheme changes after the codebase stabilizes, and not
before. The compatibility-based scheme — where an Apiary major version
names a FreeBSD compatibility line — comes later, and the alpha is
explicitly *not* part of it. The full scheme, the tag conventions, the
branch model, and the conditions under which the compatibility lines
begin are in
[`docs/release-process.md`](../release-process.md).

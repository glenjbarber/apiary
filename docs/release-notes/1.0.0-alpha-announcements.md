# Apiary 1.0.0-alpha — announcement drafts

Drafts for the LinkedIn and Facebook announcements, to be published
alongside the GitHub release.

**The house rule for these drafts: nothing in them is a claim I have
not verified.** Every capability named below is in the tree at the
release tag, and every limitation named below is a real one. An alpha
announcement that overclaims is worse than no announcement, because
the people who try it first are the people who write the issue
reports.

## The one-line description

> A FreeBSD-native cluster manager: it runs real bhyve VMs and real
> jails across a raft-consensus cluster, with a web UI, and every design
> decision written down.

## LinkedIn

---

**Apiary 1.0.0-alpha is out.**

I've been building Apiary as a home lab project, and it has reached
its first public alpha.

Apiary is a cluster manager for FreeBSD. One host is a **Comb**; one
or more Combs that have agreed to be a single cluster are a **Colony**,
with one of them holding leadership at any moment. Each Comb runs
four services — a raft consensus layer, the authority that every state
change goes through, a web UI, and a REST view of the same API.

What it actually does:

- **Real VMs and real jails, provisioned automatically.** A bhyve
  virtual machine with its own ZFS dataset, its own tap device on a
  host bridge, a VNC framebuffer for the console, and installer media
  attached as a CD-ROM or a second disk depending on what the file
  actually is — detected by sniffing the image, not by trusting its
  name.
- **Real HAST replication.** A VM can name a replica node, and its
  disk is replicated there for real. That is data redundancy, not
  automatic failover, and the difference matters.
- **A console that works from anywhere.** bhyve's VNC listener is
  loopback-only and never exposed on the network; the web UI reaches it
  through an authenticated gRPC hop, and the managerd on the far side
  independently re-validates ownership before dialling. A caller-
  supplied host or port is never accepted.
- **Joining a cluster that is safe by construction.** Joining is a
  two-person, two-code, two-approval flow, and a joining Comb receives
  the Colony's certificate authority only against a fingerprint the
  operator compared by hand.
- **A consensus layer with a colony identity.** A second raftd that
  bootstraps into a colony it does not belong to used to form a
  second, unrelated cluster that nothing could detect. Now every
  member carries a replicated colony identity, and the two are
  mutually exclusive.

The part I'm most pleased with is not a feature. It is that **186
architecture decision records** are in the repository. Every one of
them says what was decided, what was rejected and why, and what the
limits of the decision are. When something surprises me at 2am, the
answer is usually already written down — including, often, the note
that this exact thing is not solved yet.

This is an alpha. It is not a product, and it is not hardened. It
also does not have automatic failover, no scheduler, no jail console,
and a documented list of other gaps that the README states plainly
rather than hides. It targets FreeBSD 15.

If you run FreeBSD and you like reading the reasoning behind a system
rather than just the system, I would like to know what you think.

Source and release: [github.com/glenjbarber/apiary](https://github.com/glenjbarber/apiary)

## Facebook

---

**Apiary 1.0.0-alpha**

A cluster manager for FreeBSD, and my first public release of it.

A **Comb** is one FreeBSD host. A **Colony** is one or more Combs that
have agreed to be a single cluster. Apiary runs real bhyve virtual
machines and real FreeBSD jails across that cluster, provisions their
storage and networking automatically, gives each VM a browser console
that works from any machine, and replicates VM disks with HAST.

The web UI is where most of the work happens; `apiaryctl` is the
command line for the headless hosts, which is most of them.

The part I'm proudest of is the writing. There are 186 architecture
decision records in the repository, each one saying what was decided,
what was rejected, and where the decision stops working. A surprising
amount of what I know about this system I learned by reading my own
earlier notes.

It is an alpha, not a product. No automatic failover, no scheduler, no
jail console, and a plain list of other gaps in the README. It targets
FreeBSD 15.

If that's your kind of thing, I'd like to hear from you.

https://github.com/glenjbarber/apiary

## What both drafts deliberately do not say

- **No performance claims.** There are none measured.
- **No "production ready" / "battle tested" / "enterprise".** It is
  an alpha, and the project has run on a three-Comb home-lab Colony
  with real workloads — which is worth saying plainly, and is what
  the drafts say instead.
- **No claim of FreeBSD 14 support.** The compatibility floor is not
  yet decided between 14 and 15, and the drafts say "targets FreeBSD
  15" rather than picking a line that is still open.
- **No feature that is not in the tree.** The capability list was
  written from the packages and the ADR set, not from a wishlist.
